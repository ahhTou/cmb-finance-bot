# 120140A 购买页额度判断取证（2026-11-04）

本次只通过 App deep link 打开购买页，被动读取页面状态和相关前端方法源码；未点击下一步、未读取凭据、未提交、未重放接口。下文前半部保留最初分析和 mock 过程；后续实现状态见文末。

## 实测与源码对应

- 当前多次打开 120140A 都走无额度分支。新购买页首先 `readyState=complete`，但 Vue `ordInfo` 尚未收到业务数据，`viewType` 为空，购买表单不存在。不能把 DOM 加载完当成额度查询完成。
- 页面自己的 `queryBuy()` 等待查询结果；成功后将结果赋给 `ordInfo`。它先处理 `queryCode=A` 的异常及银行卡选择，然后检查 `ordInfo.ppsTag`：为 `E` 时调用 `goToAmount()` 并返回；后者跳转到无额度页。这与实测 `sfoveramount.html` 的「购买失败 / 额度不足」一致。
- 因此本版本中，新目标购买页的成功查询结果 `ppsTag=E` 是比错误页文字更早的无额度信号；不是根据金额输入框或账户余额猜测。
- 其他分支还包括风险评估、账户条件及产品交易限制。`ppsTag != E` 不能直接当作可购买。正常路径最终设 `viewType=A`，然后继续获取账户列表等数据；可购买动作仍应等待本次新页面的表单及按钮就绪，并校验产品、金额。
- 页面「单笔可购买额度」读的是 `ordInfo.posQty`。`setPosQty()` 在额度为空、为零或 ≥100 万时可能不显示，超过 10 万且低于 100 万还会向下取整为整数万。文字没出现不等于没额度，精确比较应优先用查询完成后的原始产品额度字段，不能取账户余额。本次无额度响应没有 `posQty`，缺失必须表示未知而非零。

## 测速

- 初始三次以 CDP 快照轮询，从调用打开指令开始，到新错误页文字出现约 **2.36 / 2.05 / 2.00 秒**。中间能看到旧页面与新页面同时被标为 visible，URL/visible 单独判断会出错。
- 随后复用单个 WebSocket，被动读新购买页 Vue，打开指令返回后约 **0.36–0.45 秒**捕获 `ppsTag=E`。
- 最后同一次打开的对照：**0.218 秒**文档 complete 但业务未就绪；**0.379 秒**得到 `ppsTag=E`；**0.722 秒**新错误页出现「购买失败」。此轮提前约 **343ms**获知无额度。上述计时从打开指令返回后算起，不含该指令耗时。
- 网络、缓存、采样方式和页面创建时机不同，不能承诺每轮固定节省多少。没有捕获到 120140A 有额度的当前样本，不能声称已实证正向购买分支。

## 建议实现

1. 每次打开关联本次 target + 文档代次及 URL 产品代码，拒绝旧页；CDP 连接复用，用 25–50ms 只读轮询或事件观察业务状态，避免每次枚举页面并新建连接。
2. 三态处理：查询未回/字段缺失/异常是「未知，继续等待」；匹配源码分支的 `ppsTag=E` 是「无额度」；正常 `viewType=A` + 已返回业务数据是「可购买候选」。候选仍须等本次页面控件就绪和金额/额度检查后才进入原单次提交流程。
3. 无额度判定可以提前，但不能立刻无条件重新 deep link：旧页的 `goToAmount()` 已可能向原生端发出异步跳转，下一次打开可能与它重叠。应验证旧跳转已提交/容器切换完成再发下一次打开；真实重试前须覆盖此竞态测试。
4. 保留 DOM + UiAutomator2 的业务页面确认作为兜底。无法解释的新字段、登录失效、风险/交易限制都不能当成零额度快速循环。
5. 如要接入生产，先加入单元测试覆盖旧页同产品、查询未返回、缺失 posQty、E 分支、非 E 风险分支、异步旧跳转覆盖新打开、表单加载及截止时限。正式窗口仅由账户持有人验收。
